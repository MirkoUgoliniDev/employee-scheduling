## 2. Flusso implementato (come da richiesta committente)

### Modalità differenziata (aggiunta su richiesta committente)

L'app distingue due modalità di registrazione, selezionate da `app.registration.mode`
(default `auto`):

| Modalità | DB tipico | Flusso | Email/OTP |
|---|---|---|---|
| **standalone** | SQLite desktop | username+password diretti | **Nessuna** |
| **server** | PostgreSQL | email → OTP → token → profilo | **Obbligatoria** |
| **auto** | derivata | sqlite → standalone, postgresql → server | — |

**Standalone** (installazione desktop/eseguibile locale):
- primo utente → ADMIN attivo con solo username+password;
- successivi → CAPOSALA in attesa di approvazione (l'ADMIN li attiva da /users, senza email);
- endpoint `/otp` e `/verify` → 400 `OTP_NOT_REQUIRED`; la UI nasconde i passi email/OTP
  (RegisterPage usa `status().otpRequired`).

**Server**: flusso OTP invariato + notifica email agli ADMIN attivi.

### Primo utente (installazione nuova)
```
/register → email → OTP 6 cifre → username+password     (server)
/register → username+password                           (standalone)
         → nasce ADMIN attivo (nessuno può approvarlo)
```

### Utenti successivi (CAPOSALA)
```
/register → flusso sopra
         → nasce CAPOSALA active=false ("in attesa")
         → server: notifica email a tutti gli ADMIN attivi con email
         → standalone: nessuna notifica (l'ADMIN vede la riga "In attesa" in /users)
         → l'ADMIN approva da /users (pulsante "Approva / attiva")
         → fino all'approvazione il login è bloccato (INACTIVE)
```

### Admin creati manualmente
- L'ADMIN in `UsersPage` crea utenti (ADMIN o CAPOSALA) **senza OTP**, ora con **email**
  obbligatoria nel form (usata per le notifiche). Nascono attivi.
- **`UserBootstrapService` ELIMINATO**: non esiste più un admin predefinito
  (`admin/admin123` rimosso da `application.properties`). Senza la prima registrazione
  l'app resta senza accessi.

## 4. Review avversariale — problemi trovati e fix

Eseguita con 4 agenti in parallelo (backend, frontend, script/docs, suite test).
**9 problemi reali corretti:**

| # | Gravità | Problema | Fix |
|---|---|---|---|
| 1 | CRITICAL | Build frontend rotta (`Spinner` non importato) | Import aggiunto |
| 2 | CRITICAL | Utente `active=false` poteva chiamare tutte le API (approvazione aggirabile) | `ActiveUserFilter` (403 su ogni richiesta) |
| 3 | CRITICAL | Enumerazione email: 409 restituito PRIMA del rate-limit | Rate-limit spostato prima del check |
| 4 | CRITICAL | Brute-force token `/complete` (6 cifre indovinabili) | Token 128-bit casuale + rate-limit 30/IP |
| 5 | CRITICAL | Race primo utente: due ADMIN paralleli possibili | Lock JVM con commit incluso + catch constraint → 409 |
| 6 | CRITICAL | `UsersPage` PUT riattivava silenziosamente utenti pending | `active` nullable nel DTO |
| 7 | HIGH | Race sul rate-limit (`SendWindow` non atomico) + memory leak mappe | `synchronized` + sweep oltre 1024 entry |
| 8 | HIGH | Email case-sensitive (`Mario@X.it` ≠ `mario@x.it`) | Normalizzazione + `lower(email)=lower(?1)` |
| 9 | HIGH | Lockout: ADMIN poteva auto-demotersi / rimuovere l'ultimo admin | Blocco self-demote + `USER_LAST_ADMIN` |

### Script: bug trovati e corretti

| 11 | CRITICAL | `quarkus.env.dir` non esiste in Quarkus (config mai letta) | `-Dquarkus.config.locations=<abs>/.env` + `.env` in root |

## 5. Trappole pagate (importanti)

- **Schema `app_users` in 3 posti** (V2 sqlite, V2 pg, `DemoDataRepository.ensureAppUsersTable`):
  ogni modifica futura deve toccare tutti e 3 + nuova migrazione V(N) identica nei due motori,
  altrimenti `MigrationSchemaParityTest` fallisce.
- **Quarkus Security JPA NON consulta `active` al login**: il cookie viene emesso anche per
  utenti inattivi. Il blocco reale è il filtro `ActiveUserFilter`; `/auth/me` serve solo a
  mostrare il messaggio INACTIVE al frontend. Non rimuovere il filtro credendo che `/auth/me`
  basti.
- **Lock primo utente**: `synchronized` JVM attorno a `QuarkusTransaction.requiringNew().call()`
  — il commit avviene dentro il lock. Su deploy multi-istanza PostgreSQL la gara resta
  teoricamente possibile (nessun advisory lock): documentato, non corretto (app desktop).
- **`.env` letto solo dalla CWD** (Quarkus): in dev il file deve stare nella root del progetto
  (è gitignorato); per jpackage si passa `quarkus.config.locations` con percorso assoluto.
- **Test diretti su entity richiedono transazione**: `QuarkusTransaction.requiringNew().run(...)`
  (pattern di `UsersResourceTest`).
- **`tsc --noEmit` nudo non controlla nulla** (tsconfig con `files: []` + references): usare
  `npm run build` o `tsc -b`. La build è l'unica verifica TS affidabile.
- **`databases/large_data.db` non va committato** quando cambia per uso/test locale:
  ripristinare con `git checkout -- databases/large_data.db`.

### 8.2 Trappole pagate (IMPORTANTI — costate ore di test)

1. **`mvn package` di default NON produce `*-runner.jar`**: Quarkus 3 usa fast-jar.
   Serve SEMPRE `-Dquarkus.package.jar.type=uber-jar`. Il wizard lo fa da solo.
2. **Il profilo Quarkus è BUILD-TIME** (`quarkus.flyway.locations`): la build va fatta con
   `-Dquarkus.profile=sqlite` (o `postgresql`), non basta metterlo nel `.env` a runtime.
   Errore se si sbaglia: "Found more than one migration with version 1".
3. **`quarkus.config.locations` rifiuta i backslash**: serve URI `file:///C:/...` con slash
   normali, altrimenti "SRCFG00033: Scheme C not supported".
4. **Nel `.env` i backslash nei path sono ESCAPE**: `APP_DATABASE_PATH=C:\...` diventa
   `C:employee-scheduling-...` (path rotto, DB creato con nome assurdo). Usare SEMPRE
   forward slash (`C:/employee-scheduling-data/large_data.db`) — Java/SQLite li accettano
   su Windows. Questo bug ha creato un DB spurio `employee-scheduling-datalarge_data.db`
   (rimosso e gitignorato).
5. **DB legacy senza `flyway_schema_history`** → Flyway rifiuta l'avvio ("Found non-empty
   schema but no schema history table"). Per installazioni nuove serve un DB VUOTO;
   il profilo sqlite gestisce solo DB creati da Flyway.
6. **PowerShell 5.1 + stderr nativi**: con `$ErrorActionPreference='Stop'` i warning su
   stderr (es. "Some chunks are larger than 500 kB" di Vite) diventano `NativeCommandError`
   che sembrano errori ma non lo sono. Soluzione: `Invoke-Native` (abbassa EAP localmente,
   decide solo da `$LASTEXITCODE`).
7. **`icacls` da PS 5.1**: la sintassi `(R,W)` passata come argomento fallisce
   ("Parametro non valido"). Soluzione: passare tutto a `cmd /c "icacls ..."` (parsing
   nativo), oppure `Set-Acl` (ma richiede SeSecurityPrivilege in certe sessioni).
